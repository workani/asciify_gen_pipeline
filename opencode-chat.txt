# Milking a Vision LLM into a Search-Solving Dataset Factory

Your failure isn't a ranking-tuning problem — it's an **evidence gap** problem: nothing connects what users type ("right triangle arrow") to what glyphs look like or what people call them. A vision LLM can close that gap systematically instead of hand-writing 300 entries like `_visual_aliases.mjs` does today. Here's the factory:

---

## 1. Generator A — Visual grounding pass (the core milk)

Render every search-worthy glyph large (you already have render infra), then ask the model to describe the **image without showing the formal name** first — name-first prompting anchors it into paraphrasing "BLACK RIGHTWARDS ARROWHEAD" instead of describing what humans see.

Two-stage prompt per glyph:
1. *Blind*: "Describe this symbol: shape, direction, fill/style, what everyday object/gesture/UI element it resembles. What would someone type into a symbol search box to find this? Give 10–20 phrases, casual register."
2. *Grounded*: reveal the formal name + platform renderings, let it correct/add (catches "that's called a play button").

Output lands in your existing pipeline as `characters.synonyms` (via `backfill_synonyms.mjs` → FTS rebuild) **and** as embedding documents (alias vectors). This directly fixes RC1 for both legs — ➤ gains "triangle tip arrow"-class phrases lexically, and ▶'s semantic document stops being play-button-only.

**Scale trick**: tile 20–30 rendered glyphs per image with index labels — one call yields dozens of descriptions. Unlimited budget makes dense tiling + k=3 self-consistency votes cheap.

## 2. Generator B — Query simulation (demand synthesis)

For each glyph, generate the queries that *should* retrieve it, conditioned across your own 7 golden classes (identity / visual / concept / compositional / descriptive / cultural / family) × personas (developer, designer, casual user, non-native speaker). 30–80 queries per glyph ≈ 100–250k pairs total.

Do typos, plural/singular, word-order permutations **programmatically**, not via LLM — cheaper and exhaustive.

This becomes:
- training data for embeddings/reranker,
- the expanded golden set (152 → thousands),
- regression fixtures.

## 3. Generator C — Confusion adjudication (this is the actual rank-1 decider)

The "right triangle arrow" failure is fundamentally about **competition within clusters**. So:

1. Cluster glyphs by vector neighbors + name-token overlap → families like {➤ ▶ ► ⯮ ➝ ⏩}.
2. Render the cluster as a labeled grid, present a query, ask: *"A typical person types 'right triangle arrow'. Rank these by what they most likely want, with reasoning."*
3. Sample k=5–10, aggregate into a demand distribution per (query, cluster).

This distribution is gold — it becomes:
- **graded relevance labels** (P(target|query) → grade 0–3),
- **deterministic floor data**: load winners into `unicode_search_terms` with weights — the table that exists but is wired nowhere (`lookupSearchTerms`, unused). Now `floorEverydayIntent` reads learned human judgment instead of hand-curation,

- **distillation corpus**: preference pairs (query, winner, loser) to train a small cross-encoder reranker that replaces the nondeterministic Cerebras call — deterministic, free, no budgets.

Vision is essential here: the model must *see* that ▶ is the solid play triangle while ⯮ is a two-headed specialist arrow — text names alone don't disambiguate reliably.


# The Alias-Separation Problem (Voyage index)

This is the structural flaw my probes hit: one shared index, many vector families per entity (`10148#c0–#c7`, `9654#e0–#e32`, 49k singleton aliases…), `topK=50` documents selected **before** entity dedup — ▶ couldn't get a slot while ➤'s cluster did, and no manifest describes what's actually in there. Three options, best first:

### Recommended: split into two indexes (or namespaces)

```
asciify-entities      ONE vector per entity — canonical identity doc
                      (name + glyph + category + top synonyms), atomic rebuild, manifest'd
asciify-aliases       MANY vectors per entity — visual/demand/colloquial phrases,
                      metadata: {entity: "27a4", family: "visual"|"demand"|"colloquial", gen: "v2"}
```

Runtime fuses them: query each with `topK≈25–30`, group by entity **across both result sets**, take max score per entity — uniqueness is guaranteed *by construction*, dedup-before-truncation instead of after. The crowding failure becomes impossible rather than mitigated. Lifecycle also becomes clean: regenerate the entire alias index from a new LLM run without ever touching identity embeddings; old index stays bound as instant rollback.

(Vectorize namespaces inside one index work too if you prefer fewer objects; two plain indexes is operationally simplest and keeps per-family `describe()` manifests.)

### Alternative if you refuse re-indexing now: filtered dual-query

Keep one index, backfill metadata `{family}` on existing vectors, and issue **two filtered queries** (family=base, family=alias) instead of one unfiltered. Each leg gets its own 50 slots. Weaker than the split (still one mutable blob, filters add latency) but requires no rebuild.

### Regardless of which: one-time hygiene pass

1. `describe()` + enumerate IDs by prefix family; diff against every `*vectors_manifest*.json`; delete orphaned families whose manifests were rolled back.
2. Move skin-tone stripping and FE0F normalization to **index time** (runtime currently does it post-selection — wasted slots).
3. Declare the rule going forward: *every index mutation script must write a complete manifest (build ID, model version, doc template hash) or be rejected.* This closes the "no authoritative state" gap from the handoff audit.

Migration order matters: generate the new alias corpus with the factory **first**, build the new alias index offline, A/B it through `eval_search_quality.mjs` local mode + your 60 goldens, then swap the binding. Never mutate the serving index in place during migration.

# DATASET FACTORY — Software Plan

**One-line definition:** a resumable, budget-metered generation pipeline that takes your vision LLM as an oracle and converts the Unicode corpus + your real failure telemetry into six versioned data artifacts, with your offline eval harness as the objective function deciding which generated data actually ships.

## 1. Architecture

```
                    ┌─────────────────────────────────────────┐
                    │  ORCHESTRATOR (jobs, budget, resume)    │
                    └──────┬──────────────────────────────────┘
   CORPUS ──► A. RENDER ──► B. GROUND ──► C. SYNTH ──► D. ADJUDICATE ──┐
   (ref.db)    tiles       blind+named   queries      cluster×query     │

                 │            ▼            ▼              │             ▼
                 │         E. TELEMETRY MINE ◄── events/pending/resolutions
                 │            │                            │
                 │            ▼                            ▼
                 │         F. VALIDATE ◄──── round-trip vs offline harness
                 │            │               (eval_search_quality.mjs local mode)
                 │            ▼
                 │         G. PUBLISH ──► 6 ARTIFACTS ──► staging tables ──► gates ──► prod
                 └─ raw generation log (immutable, append-only JSONL)
```

## 2. Core abstractions (everything hangs off these)

| Abstraction | Meaning |
|---|---|
| `Entity` | codepoint or sequence key, searchable flag, platform renders |
| `Run` | one LLM call: prompt hash, model, tokens, cost, raw output — **append-only, never mutated** |
| `Claim` | extracted candidate fact from a Run ("➤ means 'triangle tip arrow'"), with k-vote agreement |
| `Artifact` | published, versioned output of a stage (manifest: model, prompt_version, corpus_version, counts, eval score at publish time) |
| `Job` | resumable unit of work keyed by content hash — crash-safe, idempotent |

Rule: Claims only become Artifact rows after passing QC (§5). Raw Runs are kept forever for re-adjudication under better prompts.

## 3. Stages

### A. Render (`corpus → images`)
Select searchable subset (~20–30k: emoji + sequences + symbols/arrows/dingbats/punctuation/letterlike/accented Latin; skip unassigned/private/CJK ideographs). Render each glyph large; tile into labeled grids of ~25. Cache by glyph+platform.

### B. Ground (`images → visual claims`)
Per grid, two passes: **blind** (describe shape/direction/fill/everyday resemblance/"what would you type to find this" — formal name withheld to kill anchoring) then **grounded** (reveal name + platform variants, correct/add). k=3 votes, keep claims with ≥2/3 agreement. This industrializes `_visual_aliases.mjs` from 300 hand-written entries to the full corpus.
*Feeds: synonyms backfill, alias vectors.*

### C. Synth (`entities+claims → queries`)
Per entity: 30–80 queries across your 7 classes × 4 personas, batched 10 entities/call. Typos/plurals/reorderings generated programmatically (free, exhaustive). New axes your report proved missing: **usage-intent** ("symbol to mark right answer") and **constraint** ("thumbs up but no skin tone").
*Feeds: goldens, reranker training, alias index docs.*

### D. Adjudicate (`clusters × queries → demand distributions`) — the crown jewel
Build confusion families (vector neighbors + name-token overlap + **your thief table as seeds**). For each (query, cluster): render members side-by-side, ask who a typical user means, adaptive sampling — stop early when one target holds ≥70% across 4 votes; escalate to k=12 only for contested clusters. Output: `P(target | query)` distributions.
*This dataset does not exist anywhere in the industry. It's the moat.*
*Feeds: terms weights, guard/demotion table, resolution pre-seeds, reranker preference pairs.*

### E. Telemetry mine (`real failures → targets`)
Dedupe `unicode_search_pending` + event queries (~20k unique expected), infer intended targets with corpus context, cross-reference your 60-entry report as high-trust seed. 
*Feeds: same sinks as C/D, weighted by real demand.*

### F. Validate (`claims+queries → verified data`)
Three gates, all before any publish:
1. **Consensus** — already enforced per-stage.
2. **Round-trip** — run each query through the offline harness; retrieved ✓ keep; missed → classify *missing-evidence* (loop alias back into B/D) vs *genuinely-hard* (keep as golden).
3. **Contamination firewall** — adjudication-derived goldens are held out; generators never see them; metrics reported separately.

### G. Publish (`verified → 6 artifacts`)
Never write prod directly. Emit to staging tables, gate, then apply:

| # | Artifact | Consumer |
|---|---|---|
| 1 | `synonyms_backfill.sql` | characters.synonyms → FTS rebuild |
| 2 | alias vector corpus + full manifest | new separate `asciify-aliases` index |
| 3 | `terms_weights` (+negatives) | `unicode_search_terms` → deterministic floor |
| 4 | `guards` (thief→victim demotions) | post-fusion demotion pass |
| 5 | golden set v2 (graded, held-out split) | eval harness / CI |
| 6 | reranker preference pairs (JSONL) | distilled cross-encoder training |

Publish gate: eval must show class-level no-regression + improvement on the report buckets, else artifact is rejected with diff report.
